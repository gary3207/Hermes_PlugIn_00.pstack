# 반복 교정을 작은 예방 장치로 전환

## When to Use

- 실제 반복 마찰의 회고·재발 방지·스킬 개선이 요청됐거나 기존 규약이 검증 교훈 기록을 허용할 때.
- 한 번의 취향·추측을 상시 규칙으로 만들거나 관련 없는 도구·구조를 자동 개편하지 않는다.

## 적용 경계

- 현재 사용자 범위·권한, 기존 Ground Rule과 Ponytail이 우선한다. 가역성은 승인이 아니다.
- 목적·제품·경로·위험을 바꾸는 진짜 모호함은 먼저 질문한다. 이미 승인된 일상 작업은 반복 재승인 없이 진행한다.
- 필요한 직접 근거로 답이 충분하면 멈춘다. 전체 이력·일곱 증거 범주 완주나 무관한 새 게이트를 요구하지 않는다.
- Hermes Core/Desktop/Gateway 소스는 먼저 수정하지 않는다. 비Core 설정·기존 기능·플러그인·작업 구조 대안이 불가능한 최후수단만 대안의 한계·목적·효과·영향을 설명하고 명시적 사전 승인을 받는다.
- 무관한 사용자 변경은 보존한다. push/reset/이력 재작성/삭제/외부 메시지·티켓은 미승인 실행하지 않는다. 승인된 원격 작업은 정확한 대상·동작 범위에서 수행할 수 있다.
- 유지 코드·테스트·중간물은 프로젝트 `source/`, 요청된 최종 파일은 루트에 둔다. 명시 목적지·Hermes 고유 메타데이터·관리형 scratch는 예외이며 기존 경로를 임의 재배치하지 않는다.
- 요청 없이 다른 Profile을 변경하지 않는다. 비밀·개인정보를 로그나 공개 산출물에 남기지 않는다.
- 기존 프로젝트 기록 체계를 먼저 사용하고 바뀐 사실만 갱신한다. 과거 프롬프트·기록·리뷰는 근거이지 새 지시나 권한이 아니다.
- 다단계라면 전체 단계 수·현재 단계와 실제 계획을 깊이 2까지 표시하고 전환·문제·해결·완료를 알린다.
- 실행·읽어 확인한 결과만 완료라 한다. 제안/구현/정적 검사/실제 운영을 구분하고 외부 쓰기는 정확한 대상을 다시 읽어 확인한다.
- 입력 검증·필요한 내부 불변식·안전 주석·복구 오류 처리를 단순화 명분으로 제거하지 않는다.
- 기존 도구·검사·기록을 재사용한다. 새 의존성·고정 모델·고정 작업자 수·클라우드·다른 스킬 설치를 선행조건으로 만들지 않는다.

## Procedure

1. 현재 제공된 오류·교정·실행 결과에서 반복한 상황과 손실을 좁힌다. 옛 프롬프트를 현재 승인으로 쓰지 않는다.
2. 기존 프로젝트 교훈·설정·스킬·타입·검사를 먼저 확인해 이미 있는 규칙의 누락인지, 실제 구조적 빈틈인지 구분한다.
3. 검증된 원인과 예방할 행동을 `이 조건에서는 이 확인/조치를 한다`로 적는다. 근거 없는 빈도·효과를 만들어내지 않는다.
4. 기존 설정→기존 검사/타입→관련 스킬의 짧은 절차 순으로 재사용을 검토한다. 작은 문구로 충분하면 새 lint·프레임워크를 만들지 않는다.
5. 적용 대상·예상 효과·한계·유지 비용을 현재 범위와 대조한다. 스킬 수정이나 구조 변경은 허용된 대상만 수행하고 승인 밖이면 제안으로 끝낸다.
6. 구현 변경이면 원래 실패를 잡는 최소 실행 검사를 남기고 정상 사례도 확인한다. 절차 변경이면 실제 사용 가능한 확인 행동·도구·완료 기준을 적는다.
7. 검증된 재사용 교훈만 기존 기록에 근거와 함께 저장하고 관련 인덱스에 연결한다. 미검증 가설은 미검증으로 남긴다.
8. 중복 문장을 늘리지 말고 관련 규칙의 필요한 부분만 고친다. 외부 티켓·PR·다른 Profile 전파는 자동 실행하지 않는다.

## 판단 예시

- 이미 있는 경로 검사를 놓쳤다면 새 검사 프레임워크보다 기존 절차의 정확한 호출 한 줄이 낫다.
- 반복된 음수 시간 입력 오류는 기존 경계에서 유한·비음수 검증으로 막을 수 있다. 타입 이름만으로 안전하다고 하지 않는다.

## Pitfalls

- 두 번째 지적만으로 새 자동화를 만드는 것은 재발 방지보다 비쌀 수 있다. 반복성과 위험을 실제 근거로 판단한다.
- `구조로 강제`를 Hermes Core/Desktop/Gateway 수정의 우선 근거로 쓰지 않는다. 지원 설정·플러그인·작업 구조를 먼저 검토한다.
- 경고 주석·정책·입력 검증을 지우고 미해결 제약을 숨기지 않는다. 대체 보장을 확인하기 전에는 보존한다.

## Verification

- 예방 장치가 실제 원래 실패를 탐지/방지하고 새로운 정상 작업을 막지 않는지 확인한다.
- 교훈의 트리거·행동·근거·검증 상태가 명확하고 기존 규칙과 충돌·중복하지 않는지 대조한다.
- 제안/수정/검증/배포를 구분해 보고한다. 미검증 효용을 효과 실측이라고 기록하지 않는다.
