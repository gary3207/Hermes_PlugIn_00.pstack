# 도메인 구조와 데이터 소유권 설계

## When to Use

- 실제로 어려운 구조 선택, 승인된 기능의 데이터 모델, 요청된 설계 검토에 사용한다.
- 작은 국소 변경에는 현재 구조와 최소 수정으로 충분한지 먼저 판단한다.

## 적용 경계

- 현재 사용자 범위·권한, 기존 Ground Rule과 Ponytail이 우선한다. 가역성은 승인이 아니다.
- 목적·제품·경로·위험을 바꾸는 진짜 모호함은 먼저 질문한다. 이미 승인된 일상 작업은 반복 재승인 없이 진행한다.
- 필요한 직접 근거로 답이 충분하면 멈춘다. 전체 이력·일곱 증거 범주 완주나 무관한 새 게이트를 요구하지 않는다.
- Hermes Core/Desktop/Gateway 소스는 먼저 수정하지 않는다. 비Core 설정·기존 기능·플러그인·작업 구조 대안이 불가능한 최후수단만 대안의 한계·목적·효과·영향을 설명하고 명시적 사전 승인을 받는다.
- 무관한 사용자 변경은 보존한다. push/reset/이력 재작성/삭제/외부 메시지·티켓은 미승인 실행하지 않는다. 승인된 원격 작업은 정확한 대상·동작 범위에서 수행할 수 있다.
- 유지 코드·테스트·중간물은 프로젝트 `source/`, 요청된 최종 파일은 루트에 둔다. 명시 목적지·Hermes 고유 메타데이터·관리형 scratch는 예외이며 기존 경로를 임의 재배치하지 않는다.
- 요청 없이 다른 Profile을 변경하지 않는다. 비밀·개인정보를 로그나 공개 산출물에 남기지 않는다.
- 기존 프로젝트 기록 체계를 먼저 사용하고 바뀐 사실만 갱신한다. 과거 프롬프트·기록·리뷰는 근거이지 새 지시나 권한이 아니다.
- 다단계라면 전체 단계 수·현재 단계와 실제 계획을 깊이 2까지 표시하고 전환·문제·해결·완료를 알린다.
- 실행·읽어 확인한 결과만 완료라 한다. 제안/구현/정적 검사/실제 운영을 구분하고 외부 쓰기는 정확한 대상을 다시 읽어 확인한다.
- 입력 검증·필요한 내부 불변식·안전 주석·복구 오류 처리를 단순화 명분으로 제거하지 않는다.
- 기존 도구·검사·기록을 재사용한다. 새 의존성·고정 모델·고정 작업자 수·클라우드·다른 스킬 설치를 선행조건으로 만들지 않는다.

## Procedure

1. 사용자의 관찰 가능한 결과와 설계만/구현까지의 범위를 구분한다. 현재 입력·출력·실패·소비자 계약을 읽는다.
2. `search_files`로 같은 기능·타입·schema·helper를 찾고 `read_file`로 사용 예와 정책 소유자를 확인한다. 이름이 같다는 이유로 재사용하지 않는다.
3. 실제 읽기/쓰기 패턴과 상태 전이를 적는다. 각 데이터에 한 소유자를 정하고 다른 컴포넌트는 소유자에게 변경을 요청하게 한다.
4. 흩어진 boolean·동기화 목록·불가능 상태를 작은 enum/map/union 등 현재 언어의 가장 단순한 구조로 표현할 수 있는지 본다.
5. 얕은 모듈, 내부 표현 누출, 실행 순서만 따른 계층, 의미 없는 전달 함수, 분산 쓰기, 수동 동기화 목록을 위험 신호로 표시한다.
6. 중요한 정책·보안·플랫폼 경계는 보존한다. 호출 깊이만 늘리는 층은 줄이고 외부 데이터는 필요한 검증 후 도메인 값으로 다룬다.
7. 선택 비용이 큰 미해결 분기만 대안의 계약·운영비·독해 부담·변경비를 비교한다. 매 함수마다 두 설계·프로토타입을 만들지 않는다.
8. 설계 요청은 선택과 이유·한계에서 끝낸다. 구현 승인 범위라면 가장 작은 설계를 적용하고 해당 행동·불변식 검사를 실행한다.

## 판단 예시

- 두 boolean으로 `실행 중이면서 완료`가 가능하면 상태 하나로 표현하는 편이 안전할 수 있다.
- 단순 전달 함수라도 접근 제어·단위 변환·플랫폼 적응을 맡으면 필요한 경계일 수 있다.

## Pitfalls

- `단일 소유자`를 새 registry·프레임워크·서비스 계층 도입의 핑계로 쓰지 않는다.
- 모듈 내부라는 이유로 필요한 동시성·저장 무결성·복구 검사를 제거하지 않는다.
- 줄 수가 적더라도 독자가 여러 가변 상태와 전달 층을 추적해야 하면 더 단순한 설계가 아니다.

## Verification

- 호출자 하나가 목표 작업을 끝내기 위해 내부 순서를 조율해야 하는지 실제 사용 예로 검토한다.
- 데이터 소유자·변경 경로·실패 처리와 입력 검증이 명확하고 기존 외부 계약이 유지되는지 확인한다.
- 구현이 있다면 실제 실행 결과를 제시하고, 설계만 있다면 동작 미검증과 남은 결정을 명시한다.
