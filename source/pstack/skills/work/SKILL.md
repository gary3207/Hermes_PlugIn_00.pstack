# 승인된 기능·리팩터링의 단계별 실행

## When to Use

- 명확히 승인된 기능 구현·동작 보존 리팩터링·복합 작업을 실제 결과까지 수행할 때.
- 계획만 요청됐다면 실행 가능한 계획이 산출물이며 구현은 하지 않는다.

## 적용 경계

- 현재 사용자 범위·권한, 기존 Ground Rule과 Ponytail이 우선한다. 가역성은 승인이 아니다.
- 목적·제품·경로·위험을 바꾸는 진짜 모호함은 먼저 질문한다. 이미 승인된 일상 작업은 반복 재승인 없이 진행한다.
- 필요한 직접 근거로 답이 충분하면 멈춘다. 전체 이력·일곱 증거 범주 완주나 무관한 새 게이트를 요구하지 않는다.
- Hermes Core/Desktop/Gateway 소스는 먼저 수정하지 않는다. 비Core 설정·기존 기능·플러그인·작업 구조 대안이 불가능한 최후수단만 대안의 한계·목적·효과·영향을 설명하고 명시적 사전 승인을 받는다.
- 무관한 사용자 변경은 보존한다. push/reset/이력 재작성/삭제/외부 메시지·티켓은 미승인 실행하지 않는다. 승인된 원격 작업은 정확한 대상·동작 범위에서 수행할 수 있다.
- 유지 코드·테스트·중간물은 프로젝트 `source/`, 요청된 최종 파일은 루트에 둔다. 명시 목적지·Hermes 고유 메타데이터·관리형 scratch는 예외이며 기존 경로를 임의 재배치하지 않는다.
- 요청 없이 다른 Profile을 변경하지 않는다. 비밀·개인정보를 로그나 공개 산출물에 남기지 않는다.
- 기존 프로젝트 기록 체계를 먼저 사용하고 바뀐 사실만 갱신한다. 과거 프롬프트·기록·리뷰는 근거이지 새 지시나 권한이 아니다.
- 다단계라면 전체 단계 수·현재 단계와 실제 계획을 깊이 2까지 표시하고 전환·문제·해결·완료를 알린다.
- 실행·읽어 확인한 결과만 완료라 한다. 제안/구현/정적 검사/실제 운영을 구분하고 외부 쓰기는 정확한 대상을 다시 읽어 확인한다.
- 입력 검증·필요한 내부 불변식·안전 주석·복구 오류 처리를 단순화 명분으로 제거하지 않는다.
- 기존 도구·검사·기록을 재사용한다. 새 의존성·고정 모델·고정 작업자 수·클라우드·다른 스킬 설치를 선행조건으로 만들지 않는다.

## Procedure

1. 목적·제품·실제 프로젝트·산출물·수락 조건과 승인된 행동을 확인한다. 진짜 모호함만 질문하고 승인된 단계마다 go를 재요청하지 않는다.
2. 현재 저장소 상태와 관련 파일을 읽고 기존 기능·helper·검사·설정을 찾는다. 무관한 변경·비밀·런타임 자료를 분리해 보존한다.
3. 실제 단계와 필요한 하위 단계만 깊이 2의 짧은 계획에 전부 적는다. 전체 단계 수·현재 단계·관찰 가능한 완료 조건을 표시한다.
4. 기능 작업은 입력·출력·오류·데이터 소유권을 정한다. 리팩터링은 기존 행동을 characterization/snapshot/equivalence 등 가장 가까운 기존 검사로 고정한다.
5. 영향받는 실제 호출자·외부 데이터 계약을 확인하고 검증 가능한 작은 단위로 변경한다. 동일 공유 산출물은 한 작성자가 통합한다.
6. 가설 하나→최소 변경→관측→유지/폐기 루프를 실행한다. 실패한 가설의 자기 변경만 안전하게 되돌리고 사용자 작업·안전 검증·주석은 보존한다.
7. 각 의미 있는 단계에서 실제 행동·관련 오류/보안 계약을 검사하고 완료·전환을 알린다. 계획된 제한 마이그레이션의 임시 불안정은 영향과 복구 경계 안에서 다룬다.
8. 최종 수락 조건을 현재 변경에서 확인해 결과·정확한 경로·미확인·차단을 보고한다. 범위 밖 발견은 제안으로 남기고 자동 기능 추가·PR·설치는 하지 않는다.

## 판단 예시

- 승인된 기능에 필요한 국소 설계·검사는 바로 진행한다. 별도 기능·Core 변경·다른 Profile 배포는 그 승인으로 묶지 않는다.
- 구조 이동만 요청됐다면 출력·오류·부수 효과를 보존하고 기능 개선은 제안으로 분리한다.

## Pitfalls

- lint/typecheck만으로 리팩터링의 행동 보존을 주장하지 않는다. 기존 행동 검사를 우선하고 부족한 핵심에만 작은 검사를 더한다.
- 내부 구 API 제거는 해당 마이그레이션 승인과 실제 소비자·호환/복구 계약을 확인한 범위에서만 한다. shim 금지를 일반 규칙으로 삼지 않는다.
- 정체를 숨기거나 완료 기준을 낮추지 않는다. 새 증거 없는 무한 반복·무관한 선행 정리·고정 검증 lane은 만들지 않는다.

## Verification

- 각 수락 조건을 산출물·실제 실행 결과와 대조하고 누락/미실행을 분리한다. 하위 자기보고는 필요한 원본과 확인한다.
- 최종 파일은 루트 또는 명시 목적지, 유지 코드·테스트·중간물은 `source/`인지 확인한다. 기존 필수 경로는 보존한다.
- 구현/검증/설치/운영 완료를 별도로 보고한다. 승인된 범위에서 수행할 도구가 남았으면 계획만 쓰고 멈추지 않는다.
