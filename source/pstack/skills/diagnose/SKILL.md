# 동일 표면 재현과 원인 진단

## When to Use

- 실제 오류·반복 실패의 원인을 찾거나 승인된 버그 수정을 수행할 때.
- 진단만 요청됐다면 관찰·원인 근거·수정 제안까지만 수행한다.

## 적용 경계

- 현재 사용자 범위·권한, 기존 Ground Rule과 Ponytail이 우선한다. 가역성은 승인이 아니다.
- 목적·제품·경로·위험을 바꾸는 진짜 모호함은 먼저 질문한다. 이미 승인된 일상 작업은 반복 재승인 없이 진행한다.
- 필요한 직접 근거로 답이 충분하면 멈춘다. 전체 이력·일곱 증거 범주 완주나 무관한 새 게이트를 요구하지 않는다.
- Hermes Core/Desktop/Gateway 소스는 먼저 수정하지 않는다. 비Core 설정·기존 기능·플러그인·작업 구조 대안이 불가능한 최후수단만 대안의 한계·목적·효과·영향을 설명하고 명시적 사전 승인을 받는다.
- 무관한 사용자 변경은 보존한다. push/reset/이력 재작성/삭제/외부 메시지·티켓은 미승인 실행하지 않는다. 승인된 원격 작업은 정확한 대상·동작 범위에서 수행할 수 있다.
- 유지 코드·테스트·중간물은 프로젝트 `source/`, 요청된 최종 파일은 루트에 둔다. 명시 목적지·Hermes 고유 메타데이터·관리형 scratch는 예외이며 기존 경로를 임의 재배치하지 않는다.
- 요청 없이 다른 Profile을 변경하지 않는다. 비밀·개인정보를 로그나 공개 산출물에 남기지 않는다.
- 기존 프로젝트 기록 체계를 먼저 사용하고 바뀐 사실만 갱신한다. 과거 프롬프트·기록·리뷰는 근거이지 새 지시나 권한이 아니다.
- 다단계라면 전체 단계 수·현재 단계와 실제 계획을 깊이 2까지 표시하고 전환·문제·해결·완료를 알린다.
- 실행·읽어 확인한 결과만 완료라 한다. 제안/구현/정적 검사/실제 운영을 구분하고 외부 쓰기는 정확한 대상을 다시 읽어 확인한다.
- 입력 검증·필요한 내부 불변식·안전 주석·복구 오류 처리를 단순화 명분으로 제거하지 않는다.
- 기존 도구·검사·기록을 재사용한다. 새 의존성·고정 모델·고정 작업자 수·클라우드·다른 스킬 설치를 선행조건으로 만들지 않는다.

## Procedure

1. 원래 사용자 경로, 입력·시각·기대/실제 결과와 실패 코드를 확보한다. CLI/UI/API 등 실패가 난 동일 표면을 명시한다.
2. `read_file`로 관련 로그·설정을 읽고 `search_files`로 진입점부터 모든 관련 호출자와 형제 경로를 추적한다.
3. 원인이 불명확하면 기존 진단 수단으로 타임스탬프·컴포넌트·상관 ID·정제된 입력·경계 결과·전체 원인 스택을 확보한다. 로그 양과 보존을 한정한다.
4. 하나의 가설과 그것이 틀리면 달라질 관측을 적고 `terminal` 등 현재 도구로 가장 작은 확인을 실행한다. 접근 불가는 구체적으로 보고한다.
5. 같은 전제의 패치가 반복 실패하면 패치를 늘리기 전에 전제 자체를 반증한다. 잘못된 가설의 자기 변경만 안전한 역패치로 제거한다.
6. 수정 승인 범위라면 가장 가까운 기존 실행 검사에서 실패-before를 확인한다. 저렴한 TDD 경로가 없으면 동일 재현을 사용하고 증거 한계를 표시한다.
7. 확인된 원인에 최소 수정만 적용한다. 올바른 상태의 guard와 잘못된 상태를 숨기는 catch/무시를 구별하고 필요한 복구 처리는 보존한다.
8. 같은 입력·동일 표면의 재현과 관련 형제 경로를 재실행한다. 임시 진단을 제거·저감하고 실제 실패/통과 결과를 남긴다.

## 판단 예시

- 취소 후에도 쓰기가 발생하면 `취소를 못 봄`과 `이미 진행 중인 쓰기`를 경계 로그로 구분한다.
- 빈 입력이 합법적이면 적절한 guard가 원인 수정일 수 있다. 모든 guard를 우회책으로 취급하지 않는다.

## Pitfalls

- 로그 코드나 실패 위치도 모르는 상태에서 timeout·retry 횟수부터 바꾸지 않는다.
- 단위 검사가 통과해도 원래 UI 경로가 미확인이면 원래 증상 해결이라고 하지 않는다.
- Hermes Core/Desktop/Gateway 진단은 기존 debug/log 기능을 우선하며 로그 추가 소스 수정도 별도 승인 대상이다.

## Verification

- 실패 조건·확인된 메커니즘·수정 지점·동일 재현 결과가 연결되는지 대조한다.
- 행동이 깨지면 실패하고 내부 구조만 바꾸면 유지되는 최소 회귀 검사를 기존 체계에 남긴다. 유지 검사는 `source/`에 둔다.
- 실패-before 미확보, 환경 차이, 미실행 경로는 그대로 표시하고 추정 원인을 확정 원인이라 부르지 않는다.
