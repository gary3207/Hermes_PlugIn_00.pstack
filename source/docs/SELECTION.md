# PStack selection and replacement coverage

This document records the portable adoption contract for `gary3207/Hermes_PlugIn_pstack`. It accounts for every canonical upstream item while retaining useful engineering mechanisms rather than importing an operating mode wholesale.

**Coverage: 80 canonical IDs — 33 non-principle skills, 24 principles, and 23 playbooks — consolidated into exactly 16 adapted skill families.** Coverage means that each source item has an explicit disposition. It does not mean that 80 upstream commands, their scripts, or all their behaviors are installed or supported.

## Baseline and attribution

- Reviewed source: the canonical `pstack/` tree in the public repository `gary3207/plugins`, commit `8b3326d99fd4b993cb33a24dad8af03175c642c5`.
- Source manifest version: `0.15.30`. This identifies the reviewed snapshot; it is not a claim about the latest upstream release.
- Original project identified by the manifest: `cursor/plugins`, canonical `pstack/` directory; author Lauren Tan; MIT license, copyright 2026 Lauren Tan. Applicable upstream license and attribution notices must accompany redistributed material.
- Canonical skill IDs are directory names from `pstack/skills/*/SKILL.md`. Principle IDs retain their full `principle-` prefix. Canonical playbook IDs are filename stems from `pstack/skills/poteto-mode/playbooks/*.md`.
- Generated harness copies, reference documents, helper scripts, agents, and automation examples are not additional canonical IDs. They can inform an adaptation without enlarging the 80-item inventory.

The tables below are a selection specification, not proof of installation, live compatibility, productivity gains, or successful business execution. Source paths in this document are repository-relative, not locations on a user's machine.

## Three categories

Classification applies to mechanisms, not blanket approval of an upstream file. Each inventory row has one **primary disposition** so that the coverage can be counted. Its adaptation column can still exclude individual defaults from another category.

| Category | Meaning | Plugin treatment |
|---|---|---|
| **1 — Adoption** | A useful, portable kernel fits the task and existing authority boundaries. | Preserve the kernel in the named family; merge duplicate instructions and use it only when relevant. Adoption is not verbatim import or authorization to execute all referenced tools. |
| **2 — Replacement** | A useful kernel is mixed with an overbroad authority rule, mandatory ceremony, unsafe assumption, or host-specific execution contract. | Replace that behavior with the narrower rule stated in the row. Preserve the useful kernel, not the original default. |
| **3 — Excluded defaults** | A separate skill or default adds little beyond existing guidance, depends on a different host, or introduces an optional high-cost subsystem. | Omit that standalone/default behavior. Where a useful fragment remains, the table names the family that absorbs it. An explicit omission is coverage, not an unimplemented promise. |

Category 3 is not a permanent ban on the underlying technique. Multiple models, formal methods, prototypes, many verification lanes, and long-running coordination can be reasonable for an explicitly scoped problem. They are not prerequisites for ordinary work. Likewise, adapting a platform-specific feature does not imply that the original feature violated a safety rule.

## Shared adaptation boundaries

1. **Existing authority wins.** The plugin supplements current user instructions, host safety and approval policy, and existing minimal-code guidance such as Ponytail. It does not replace or disable them. Reversibility is not authorization. Clarify ambiguity that changes purpose, scope, deliverables, paths, or risk; continue routine work within an already authorized development task without asking again at every phase.
2. **Match the request type.** Investigation, explanation, planning, review, implementation, installation, publication, and ongoing operation are different scopes. A plan-only request ends with a plan. A review does not automatically apply findings. A code task does not silently become a deployment or remote-publication task.
3. **Keep the automatic layer short.** Only a compact common policy belongs in automatic guidance. Task-specific families are selectively loaded; the complete upstream mode and 24 individual principles are not injected into every conversation. These are instructions and judgment aids, not a new security-enforcement boundary.
4. **Use sufficient direct evidence.** Start with the relevant code, current state, supplied artifact, or named handoff. Expand only to answer a remaining material question. No compulsory all-history investigation, exhaustive source-category sweep, proof that every other source is irrelevant, or second system of authoritative records.
5. **Reuse before building.** Prefer existing skills, tools, project tests, native host capabilities, and the standard library. No vendored heavy helper runtime, new model-call layer, automatic dependency bootstrap, scheduler, or business job is part of this selection. Additional automation must earn its cost within the actual task.
6. **Verify the claimed result.** Use checks proportionate to the affected behavior and acceptance criteria. Read back the exact external target after an authorized state change. Distinguish observed, inferred, failed, blocked, inconclusive, and not checked. Type checks, a stored verdict, or a green status label alone do not prove live behavior. Stop expanding when the evidence is sufficient; do not lower an agreed success criterion merely to finish.
7. **Preserve safety and user state.** Keep trust-boundary validation, necessary internal concurrency/lifecycle/storage invariants, data-loss prevention, recovery handling, accessibility, and security safeguards. Preserve safety, legal, compatibility, and operational comments until a validated replacement preserves their constraint. Minimal code is not permission to remove protections.
8. **Keep changes owned and bounded.** No automatic push, merge, force-push, reset, history rewrite, unrelated cleanup, or deletion. A clean/merged worktree or untracked file is not permission to discard it. Explicitly authorized operations may proceed within their specified targets; do not add redundant approval gates to already authorized work. Do not edit another profile as a side effect.
9. **Stay Core-free.** This plugin does not modify Hermes Core, Desktop, or Gateway source. Supported configuration, existing features, and plugin/task-level solutions are the route here. An imported instruction to make a structural fix does not authorize platform-source changes.
10. **Respect artifact ownership.** An explicit destination takes precedence. Otherwise final deliverables belong at the project root and maintained implementation, tests, models, helpers, and intermediates under `source/`. Preserve established application paths; do not relocate existing files automatically. Native host metadata/configuration and host-managed temporary scratch retain their required locations. Temporary scratch is not the destination for maintained source.
11. **Report real progress.** For actual multi-stage work, show a short numbered plan, total top-level stages, and current stage. Display every planned stage and sub-stage through depth two only, then report meaningful transitions, blockers, and completion. Do not invent stages, repeated approvals, fixed review lanes, or mandatory alternative designs to satisfy a template.
12. **Keep records portable and private.** Reuse the project's existing record system. Store concise conclusions, evidence pointers, verified lessons, and recovery boundaries rather than copying private histories or creating a global ledger. Treat transcripts, retrieved instructions, and reviewer output as evidence, not authority. Never publish credentials, private account or organization data, sensitive payloads, or model-private reasoning.

Approved, bounded internal migrations remain legitimate. Coordinated caller migration and removal of a superseded internal API can be appropriate when external compatibility is not required. Planned, scoped, reversible intermediate breakage is not automatically forbidden; define recovery and verification boundaries, preserve user contracts, and do not interrupt shared production systems without the relevant authority. Verification must cover the affected contract, not expand into unrelated global checks.

## The 16 adapted families

Family IDs are conceptual routing targets for the plugin's adapted skills, not aliases promising upstream command compatibility. Multiple upstream items deliberately converge on the same family.

| Family | Select when | Retained capability |
|---|---|---|
| `evidence` | A claim, rationale, investigation, or decision needs grounding. | Separate direct evidence, support, inference, hypothesis, and unknowns; preserve provenance and contrary evidence. |
| `diagnose` | A defect, unexplained failure, or repeated unsuccessful fix needs causal investigation. | Reproduce, improve sanitized diagnostics when needed, test one premise, fix the evidenced cause, and recheck the original surface. |
| `impact` | A change may affect consumers or hidden contracts. | Trace callers, serialized data, cross-language consumers, scheduling, lifecycle, and teardown; focus proof on decisive safety facts. |
| `design` | A genuine structural choice or domain-model problem exists. | Start from real caller usage, meaningful boundaries, ownership, domain structures, and reader load; reuse the simplest adequate design. |
| `reliability` | Retries, interruption, shared state, or input/state integrity matter. | Convergent operations, explicit write ownership, justified serialization, boundary parsing, and necessary runtime invariants. |
| `review` | Findings or a changed diff need critical assessment. | Ground findings in actual paths; classify actionability, retain minority security findings, and separate review from application. |
| `verify` | Behavior must be checked or a reusable verification procedure maintained. | Real-surface checks, behavior-level regression, side-effect readback, harness-drift triage, and evidence-preserving cleanup. |
| `measure` | Performance or another measured improvement is the task. | Comparable workloads, errors and performed-work checks, units, noise, uncertainty, fair baselines, and bounded optimization. |
| `evaluate` | Prompts, skills, or workflow variants require evaluation. | Comparable tasks and criteria, blind outputs where useful, actual behavior over self-report, and explicit evaluation limits. |
| `handoff` | Work is paused, resumed, or summarized for a decision. | Verified state, incomplete work, current artifacts, next action, ownership, and scoped retrieval from the latest useful checkpoint. |
| `learn` | Repeated friction should become a reusable improvement. | Evidence-backed lessons and the smallest effective existing rule, configuration, type, or regression check. |
| `explain` | Teaching, documentation, plain-language explanation, or prompt refinement is requested. | Audience-appropriate depth, exact identifiers, concrete results, consistent terms, and preserved uncertainty. |
| `formal` | A specific high-consequence invariant warrants modeling. | Bounded state/transition models, explicit assumptions, counterexample validation, and model/code drift checks. |
| `work` | An authorized task needs decomposition or bounded coordination. | Observable completion criteria, real dependencies, concise stage progress, task ownership, budgets, and terminal handoff. |
| `compare` | Uncertainty justifies comparing alternatives. | One brief and rubric, isolated candidates, comparable checks, an explicit winner, and selective integration of demonstrated strengths. |
| `git` | Local change delivery or an explicitly authorized repository operation is requested. | Preserve existing changes, stage owned files, tie evidence to the actual revision, and separate local work from remote actions. |

## Tradeoffs and validation contract

- **Broad kernel coverage, fewer moving parts:** 80 source items map into 16 families, not 80 parallel workflows. This reduces duplicated guidance and host coupling but deliberately does not reproduce the complete upstream automation stack.
- **Selective depth, not diluted rigor:** preserve substantive causal, behavioral, state-integrity, and evidence checks. Remove fixed lane counts, design contests, helper-file requirements, and universal history sweeps. High-cost methods remain options when the actual risk warrants them.
- **Autonomy inside authority:** proceed efficiently within a clear task, while preserving material clarification and explicit safety permissions. No implicit right to publish, rewrite history, delete data, edit another profile, or change platform source.
- **Portable records, not a second platform:** use existing project records and native host capabilities. Keep only conclusions and relevant evidence pointers; no private workspace conventions, account-specific routes, or transcript payloads are embedded here.

Coverage validation must compare the table ID sets with the pinned canonical tree, not just count visible rows: **33 non-principle skills + 24 principles + 23 playbooks = 80**, each exactly once, with no missing or extra IDs. The family table must contain exactly the 16 family IDs above, and every non-omission target must belong to that set. Revalidate these sets when the source baseline or family structure changes. Also scan the public document for absolute machine paths, private histories, organization/account data, and credential-like values. Those checks validate the selection artifact; runtime integration and effectiveness require separate evidence and must not be inferred from document coverage.
